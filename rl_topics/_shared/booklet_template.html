01The big picture in one page

If you remember only one page, remember this one.

Both projects try to answer the same question: "In every square, which move is best?" The answer is called a policy (a plan: one arrow per square). Both use the Bellman equation to find it. The only real difference is what the agent is allowed to know at the start.

The one sentence

Value iteration is given the rule book, so it calculates every square, every action and every possible slide at once, without ever playing. Q-learning is not given the rules, so it plays, and after each real move it uses Bellman to correct one number. Thousands of games later it reaches the same plan.

Why bother with Q-learning?

Because in the real world there is almost never a rule book. Nobody can write transitions() for a walking robot, a video game seen as pixels, or a stock market. Q-learning (and its big brothers DQN and PPO) works when you don't know the rules, which is the situation RL is really for.

What does "r + γ · V(s′)" return?

A number, not an action or a state. It is the score of one move: "reward now + everything I can collect after." Note it is γ × the value of the next state, not × the next reward. V(s′) already contains the whole future:

V(s′) = r′ + γ·r″ + γ²·r‴ + …   so   r + γ·V(s′) = r + γ·r′ + γ²·r″ + …  (the whole future)

The rules we wrote:

  • 20 cells − 3 walls = 17 states; goal and pit end the game, so 15 playable squares.
  • Goal +1, pit −1, every other step −0.04 (so wandering costs a little).
  • Bumping a wall or the edge: you stay put.
  • Slip rule (one rule for every square): slip = 0.4 → 60% where you aim, 20% slide to each side.

The rule book is a function: transitions(s, a)

We didn't type a table of probabilities for every square. We wrote a few general rules, and this function works out the answer for any square and action on demand:

def transitions(self, s, a):
    """P(s' | s, a) and R as a list of (probability, next_state, reward)."""
    if self.slip == 0:
        outcomes = [(1.0, a)]                                  # normal floor: always where you aim
    else:
        left_of, right_of = (a - 1) % 4, (a + 1) % 4           # the two sideways directions
        outcomes = [(1 - self.slip, a), (self.slip / 2, left_of), (self.slip / 2, right_of)]
    result = []
    for p, actual in outcomes:
        s2 = self._move(s, actual)                             # where that direction takes you (walls → stay)
        result.append((p, s2, self.reward(s2)))               # reward for ARRIVING at s2
    return result

Ask the rule book a question (slippery floor, the square next to the pit, aiming up):

transitions((1,3), up)   = [ (0.6, (0,3), −0.04),     60%: up, as aimed
                             (0.2, (1,2), −0.04),     20%: slide left
                             (0.2, (1,4), −1.00) ]    20%: slide right → INTO THE PIT

transitions((1,3), left) = [ (0.6, (1,2), −0.04),     60%: left, as aimed
                             (0.2, (1,3), −0.04),     20%: slide down → wall → stay
                             (0.2, (0,3), −0.04) ]    20%: slide up      → never the pit!
Who gave the rule book, and when?

We wrote it, in gridworld.py. Value iteration reads it every time it calculates a Q-value (next section, the env.transitions(s, a) call). The policy was not given; it is the output.

05Value iteration: the code, line by line

value_iteration.py: four small functions, and the whole algorithm fits on half a page.

def q_value(env, V, s, a, gamma):                                     # ① score ONE action
    return sum(p * (r + gamma * V[s2]) for p, s2, r in env.transitions(s, a))

def bellman_sweep(env, V, gamma):                                     # ② one pass over EVERY square
    new_V = dict(V)
    biggest_change = 0.0
    for s in env.states:
        if env.is_terminal(s):
            continue                                     # goal/pit: no future, value stays 0
        new_V[s] = max(q_value(env, V, s, a, gamma) for a in ACTIONS)
        biggest_change = max(biggest_change, abs(new_V[s] - V[s]))
    return new_V, biggest_change

def greedy_policy(env, V, gamma):                                     # ③ turn values into arrows
    return {s: max(ACTIONS, key=lambda a: q_value(env, V, s, a, gamma))
            for s in env.states if not env.is_terminal(s)}

def value_iteration(env, gamma=0.9, theta=1e-6):                     # ④ the whole algorithm
    V = {s: 0.0 for s in env.states}                  # start knowing nothing
    while True:
        V, change = bellman_sweep(env, V, gamma)
        if change < theta:                            # settled? stop
            break
    return V, greedy_policy(env, V, gamma)
PieceWhat it doesBellman part
① q_valueAsks the rule book for every possible landing spot, and averages reward + γ·V(landing) weighted by its probability. The highlighted call is where the rule book is read.Σ P(s′|s,a)·[r + γ·V(s′)]
② bellman_sweepFor every square: score all 4 actions, keep the biggest. Also measures the biggest change. Uses the old V for all squares (writes into new_V), so every square in a sweep sees the same snapshot.max over a
③ greedy_policyAfter values settle, for every square pick the action with the biggest score. This is the policy.argmax over a
④ value_iterationStart at 0 everywhere, sweep, sweep, sweep… until the biggest change < θ.repeat until converged

What you are seeing

  • Every sweep calculates ALL squares, but only squares that can "see" a known value get a good number. Squares far away just collect −0.04 per sweep, because their neighbours still know nothing.
  • The good news ripples backwards one square per sweep (blue outlines): sweep 1 the square next to the goal, sweep 2 the next ring, and so on. Each value is 0.9 × the one after it, minus 0.04: 1.00 → 0.86 → 0.73 → 0.62.
  • "Biggest change" is the largest amount any single square moved in that sweep: 1.000, 0.900, 0.810, 0.729. It shrinks by ×0.9 (= γ) each sweep. When it falls below θ = 0.000001 the values have settled. Here that took 9 sweeps.
  • Work per sweep: 15 playable squares × 4 actions = 60 Bellman scores (on ice each averages 3 slides). The slippery run needed 49 sweeps ≈ 2,940 scores: a fraction of a second, because it's just arithmetic.

To the Q-learning agent, the game looks like this, and nothing more:

"I'm in state 0. I pressed action 2. Now I'm in state 1, reward 0."
"I'm in state 1. I pressed action 1. Now I'm in state 5, reward 0, game over."   ← it doesn't know 5 is a "hole"

It just learns that going to state 5 leads to nothing good. That's why the same q_learning.py worked on Taxi without a single change: it never needs to know what a lake or a taxi is, only state numbers, action numbers and rewards.

FrozenLake has a rule book too, but it's hidden

The Gymnasium authors wrote FrozenLake's rules (env.unwrapped.P). Inside env.step(), the game secretly rolls the dice using them. Q-learning never reads them. The one exception is Part 3 of frozen_lake.py, where we deliberately peeked to build an answer key with value iteration.

Why Q(s,a) and not V(s)?

With V you'd only know "square 14 is good". To pick a move you'd need to know which action leads to which square, and that's the rule book you don't have. Q stores the answer per action directly: "from 14, right is worth 1.00". So you can pick the best move by just looking at a row of the table. That's why Q is a 16 × 4 table (64 numbers) for FrozenLake and 500 × 6 (3,000 numbers) for Taxi.

08Q-learning: the code, line by line

q_learning.py: shared by FrozenLake and Taxi.

① Choosing a move: ε-greedy

def epsilon_greedy(Q, s, eps, rng):
    if rng.random() < eps:
        return int(rng.integers(Q.shape[1]))         # EXPLORE: random action
    best = np.flatnonzero(Q[s] == Q[s].max())         # EXPLOIT: the best action(s)…
    return int(rng.choice(best))                      # …ties broken randomly (at the start ALL are 0)

② Training: the whole algorithm

def train(env, episodes, alpha=0.1, gamma=0.99, eps_start=1.0, eps_end=0.05, eps_decay=0.999, seed=0):
    rng = np.random.default_rng(seed)
    Q = np.zeros((env.observation_space.n, env.action_space.n))      # 16×4 table of zeros: knows nothing
    eps = eps_start                                                   # start fully random

    for ep in range(episodes):                                         # one GAME
        s, _ = env.reset()
        done = False
        while not done:                                                # one STEP
            a = epsilon_greedy(Q, s, eps, rng)                        # 1. choose
            s2, r, terminated, truncated, _ = env.step(a)              # 2. act, 3. see

            target = r + gamma * np.max(Q[s2]) * (not terminated)     # 4. Bellman target
            Q[s, a] += alpha * (target - Q[s, a])                     # 5+6. surprise → nudge

            s = s2                                                    # 7. move on
            done = terminated or truncated
        eps = max(eps_end, eps * eps_decay)                           # explore a bit less next game
    return Q, episode_rewards
LineMeaning
Q = np.zeros(...)One number per (state, action), all 0. These zeros are placeholders, not knowledge.
env.step(a)The only contact with the world. The game rolls its hidden dice and returns where you landed and the reward. Compare with project 2's env.transitions(s, a), which returned all outcomes with probabilities.
np.max(Q[s2])Best score stored for the square you landed on. This is only read, nothing is calculated for s2. It's the "Q-max" part.
* (not terminated)If the game really ended (goal or hole), there's no future: target = r. If it was only truncated (time limit), the future still counts.
target - Q[s, a]The surprise: how much better or worse the move went than expected.
Q[s, a] += alpha * …Move the old guess 10% (α = 0.1) toward the target. Only one number changes per step: the state you left, for the action you took.
eps * eps_decayε: 1.0 → 0.05 over the games. Explore early, exploit later.

③ Testing: evaluate()

Plays 1,000 games using np.argmax(Q[s]) every step, with no exploration and no learning. This is the "exam". Training scores are lower because training still makes random ε moves.

09Q-learning: how the goal's value travels back

It updates after every step, and the goal's value still ends up flowing backwards. Here is how.

The 3-state story

   A  ──►  B  ──►  C (GOAL, +1)          (to keep it simple: γ = 1, α = 1, all Q start at 0)

Game 1   A → B :  target = 0 + Q[B] = 0 + 0 = 0   → Q[A] = 0      (B knows nothing yet)
         B → C :  target = 1  (goal!)             → Q[B] = 1  ★   (only B learns)
Game 2   A → B :  target = 0 + Q[B] = 0 + 1 = 1   → Q[A] = 1  ★   (A learns, never saw C)

A never looked at C. It only looked at its neighbour B, and B had already learned about C. Each square only needs its next neighbour's number. Q[s2] is a stored summary of the whole future from s2, like asking a neighbour "how far to the station?" and adding your own walk to their house.

But s2 can only know the future if someone went there first

Before a square has been visited, its Q is just the starting 0, a placeholder. Updates that read it learn from nothing (game 1, A → B above). Knowledge has to be built from the goal backwards, by actually walking there. That's why Q-learning needs exploration and many games. Using your own current guesses like this is called bootstrapping.

Correcting a common picture

Not: "play until the goal, then calculate everything backwards." There's no backwards code anywhere.
Actually: it updates after every single step. The backwards flow happens across games: each game that passes through pushes the news one more square back. (The "play to the end, then update everything backwards" method also exists. It's called Monte Carlo.)

Why every square eventually gets learned

ε forces random moves. Without it the agent would walk the same few paths forever, and squares it never visited would stay 0 forever. In the playground (playground.html), set ε to 0 after a reset and you can watch it get stuck, never discovering the goal.

13Clearing up the confusions

Every question asked while building these projects, with the short, correct answer.

Does Bellman calculate the probability of the next state, or the value?

The value. Probabilities are inputs, given by the world's rules; nobody calculates them. Bellman asks: "given these dice, how good is it here?" The probabilities are just weights in the average.

What does r + γ·V(s′) return: an action or a state?

Neither, a number: the score of one move ("reward now + everything after"). Compare the numbers for all actions: max gives the state's value, argmax gives the action. The game then gives you the next state. And it's γ × the next state's value, not its reward.

Is Bellman calculated for all possible actions?

Value iteration: yes, every square × every action × every slide, every sweep (60 scores per sweep here). Q-learning: no, only the one action you took. max(Q[s2]) looks at all actions of s2, but only reads stored numbers.

In Q-learning, is Bellman calculated after taking the action, to see how it went?

Yes. Choose → act → see r and s2 → Bellman target → compare with the old guess → nudge 10%. It has to come after, because only the game can provide r and s2. "How it went" means reward plus how good the new spot looks, which matters because FrozenLake gives r = 0 on almost every step.

Does it wait until the goal is reached and then calculate backwards?

No. It updates after every step. The backwards flow happens across games: game 38 taught square 14, game 43 square 10, … game 70 the start. Waiting for the end and then updating everything is a different method, Monte Carlo.

Which state gets updated: the one I just reached, or the previous one?

The previous one, the state you just left (Q[s, a] += …). The state you landed in (s2) is only read for its best score. You can only judge a move after you see where it took you.

Bellman needs the future all the way to the goal. How can one step ahead be enough?

Because Q[s2] is already a summary of the whole future from s2. You don't need to touch far-away states; s2's number contains them. A learned about C by looking only at B (section 09).

But s2 can't know the future if it has never been there!

Exactly right, and that's Q-learning's main weakness. Until visited, Q[s2] = 0 is a placeholder; updates using it are temporarily wrong and fixed later. That's why exploration (ε) and many games are needed, why Taxi learned only 400 of 500 states, and why play.py's coach sometimes says "I never visited this spot".

So it wanders, then slowly learns each square's probabilities and action probabilities?

It wanders, yes. But it learns scores (Q-values), not probabilities. Slide chances are never stored; they get "baked into" the scores by averaging. Actions are chosen by biggest score, not by probability. (Policy methods like PPO do learn action probabilities, like "70% right, 30% down". The ice's probabilities always belong to the world.)

Is the only difference between the projects "one at a time" vs "all at once"?

It's a real difference, but a consequence. Root cause: project 2 has the rule book, project 3 doesn't. Also, it's one at a time in outcomes too: value iteration averages all 3 slides, Q-learning learns from the one that happened.

So project 2 creates the rule book, and project 3 learns by playing?

Flip the first half: project 2 is given the rule book (we wrote it in gridworld.py). Both create the same thing: a plan (values + arrows).

What was the policy in project 2? Did we give it?

No. The policy is the output: greedy_policy() picks the biggest-scoring action in each square after the values settle.

In FrozenLake, is the only unknown where the end is?

Everything is unknown: goal, holes, what actions do, the grid shape, slip chances, rewards. It only knows "16 states, 4 actions, I'm in state 5".

What is the "biggest change"?

In one sweep, the largest amount any single square's value moved. It's the "are we done yet?" meter: 1.000, 0.900, 0.810, 0.729 … (shrinking by γ). Below θ = 0.000001 → stop.

Does each sweep calculate only the squares near the goal?

No, every sweep calculates every square. But a square only gets a good number once a neighbour has one, so the good values appear one ring further back per sweep. Far squares just keep collecting −0.04 until the news arrives.

What if the goal is 1,000,000 steps away?

Plain methods mostly fail. (1) The discount shrinks it: 0.991,000,000 is exactly 0 in a computer. (2) Value travels back one step per update, and random exploration would almost never get that far. Real RL uses step penalties (like Taxi's −1), reward shaping, Monte Carlo / multi-step updates, neural networks that generalise, and sub-goals.

Does Google Maps wander like Q-learning?

No. It has the full map, so it's model-based, like project 2: it calculates without driving.

Cheat sheet

Value iteration 
V = 0 everywhere
repeat:
  for every state s:
    V(s) = max over a of
      Σ P(s′|s,a)·[r + γ·V(s′)]
until biggest change < θ
policy(s) = argmax over a

Needs: the rule book. Knobs: γ, θ.
Output: V + arrows. Exact.

Q-learning 
Q = 0 everywhere
for each game:
  for each step:
    a = ε-greedy(Q[s])
    s2, r = env.step(a)
    target = r + γ·max Q[s2]
    Q[s,a] += α·(target − Q[s,a])
    s = s2
  ε = ε × decay

Needs: only the game. Knobs: γ, α, ε.
Output: Q + arrows. Approximate.

The four sentences to remember
  1. Bellman calculates a value (a number); probabilities and rewards are given; the action is the argmax.
  2. Value iteration has the rule book, so it calculates every square, action and slide, sweep after sweep, without playing.
  3. Q-learning has no rule book: after each real move, it updates the state it left using the best stored score of the state it landed in.
  4. In both, the goal's value flows backwards one step at a time: per sweep in value iteration, per game in Q-learning.
