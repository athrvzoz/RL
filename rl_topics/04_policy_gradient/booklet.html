01The big picture

Two families of RL. You've only met one so far.

Everything you've built so far is value-based: learn a score for each action (Q), then choose the action with the biggest score (argmax). The policy is a side effect of the scores.

Policy-based methods skip the scores. The agent directly holds a probability for each action in each state, like "push left 30%, push right 70%", and learns those probabilities. It plays by rolling its own dice.

Why would you want that?

ProblemValue-based struggles because…Policy-based…
The best play is random (rock-paper-scissors, bluffing in poker)argmax always picks the same move, and a smart opponent exploits itcan learn "1/3 each"
Continuous actions (steering angle, motor force)max over infinitely many actions is impossibleoutputs a distribution, e.g. "mean 12°, spread 3°"
Small score changes flip the actionQ(left) = 3.20 vs 3.21 flips the choice completelyprobabilities change smoothly
Language models (chat assistants)"Q for every possible next word" is awkwarda language model already is a policy: probabilities over the next word
The one sentence

REINFORCE plays a whole game by rolling its own dice, then increases the probability of every action that was followed by a better-than-usual result, and decreases it for actions followed by a worse one. The size of each change is set by the policy gradient: (result − baseline) × ∇log π(a|s).

03Intuition: when random is best

Real output of python rps.py.

Rock-paper-scissors against a spy

The opponent is a "spy": it looks at which move you've played most so far and plays the move that beats it. Three fixed policies, 3,000 rounds each (win +1, draw 0, lose −1):

Your policyAverage score per round
always rock (what argmax Q would do)−1.000 (loses every round)
70% rock, 30% paper−0.701
1/3 each (random)+0.001 (can't be exploited)

A deterministic policy, which is all Q-learning's argmax can give you, is the worst possible here. Only a random policy is safe. A policy-based learner can represent it; a value-based learner can't.

The coach analogy

A cricket coach doesn't calculate the exact value of every shot. After a match they say: "the innings went better than usual, so play more of the shots you played today; it went worse, so play fewer of them." Over many matches, good shots get more frequent. That's REINFORCE: reinforce what came before good results.

Two kinds of probability: keep them apart

The agent's probabilities π(a|s): its own dice, which REINFORCE learns ("push right 70%"). The world's probabilities: how the environment responds (FrozenLake's slip chances, the dealer's cards). Those belong to the world, are never learned directly, and REINFORCE doesn't even need to know them.

04Maths I: softmax, scores → probabilities

The maths: the exponential function and fractions.

A network's raw outputs (logits) can be any numbers: 2, −1, 0.5. Probabilities must be positive and add up to 1. Softmax fixes both:

π(a)  =  eha  /  ( eh1 + eh2 + … )        e ≈ 2.718
         ▲ always positive          ▲ dividing by the total makes them add up to 1

Worked example 1: three logits

h = [2, 1, 0]
e2 = 7.389     e1 = 2.718     e0 = 1.000         total = 11.107
π = [7.389/11.107, 2.718/11.107, 1/11.107] = [0.665, 0.245, 0.090]      sum = 1 ✓
  • Bigger logit → bigger probability, but no action ever gets exactly 0, so it keeps exploring a little by itself.
  • Adding the same number to every logit changes nothing: [12, 11, 10] gives the same π. Only differences matter.
  • Equal logits → equal probabilities: [0, 0, 0] → [1/3, 1/3, 1/3].

The gradient of log softmax (needed in chapter 05)

∂ log π(a) / ∂ hb  =  1 − π(b)    if b = a   (the chosen action)
                        =   − π(b)    if b ≠ a   (every other action)

In words: raising the logit of the chosen action raises its log-probability (by 1 − π(a)); raising any other logit lowers it. For h = [0, 0, 0] and chosen action 1: ∇log π = [−1/3, +2/3, −1/3].

05Maths II: the policy gradient

The maths: averages (expectation), derivatives and the chain rule for log.

Step 1: what we want to maximise

Start with a bandit (one decision, then the game ends). Expected reward under policy θ:

J(θ) = Σa πθ(a) · R(a)          "probability of each action × its average reward, added up"

Step 2: take the derivative

∇J(θ) = Σa ∇πθ(a) · R(a)          R(a) is the world's, it doesn't depend on θ

Problem: this needs R(a) for every action. But we only get to try one action per game, and we don't know R.

Step 3: the log-derivative trick

from school:  d/dx log f(x) = f′(x) / f(x)      so      ∇π = π · ∇log π

∇J(θ) = Σa πθ(a) · ∇log πθ(a) · R(a)
      = average over actions drawn from π of [ R · ∇log π(a) ]        ← "Σ π(a) × something" is an average!
Why this trick is everything

An average over actions drawn from π can be estimated by actually drawing actions from π, i.e. by playing. So: roll your dice, get reward R, compute R·∇log π(a) for the action you took. On average, that points exactly uphill. No knowledge of R for other actions, no rule book.

Step 4: the REINFORCE update

θ  ←  θ  +  α · G · ∇ log πθ(a | s)          for a whole game: add this up over every step t
          ▲ step size  ▲ how good   ▲ "which way to turn the knobs to make action a more likely"

Worked example 2: one bandit update (real output of bandit_pg.py)

preferences h = [0, 0, 0]  →  π = [0.333, 0.333, 0.333]
rolled the dice: picked arm 1, got reward r = 3.0
∇log π(arm 1) = [−0.333, +0.667, −0.333]               (chapter 04's formula)
no baseline:  h += 0.1 × 3.0 × ∇  → h = [−0.1, 0.2, −0.1]  → π = [0.299, 0.403, 0.299]

Arm 1 went from 33.3% to 40.3%, and the other two went down to keep the total at 1. A bigger reward would have pushed harder.

06Maths III: returns-to-go and the baseline

Two small changes that make REINFORCE far less noisy.

Returns-to-go: don't blame an action for the past

In a game with many steps, the action at step t can only affect rewards from t onward. So weight it by Gt, not by the whole game's total:

Gt = rt + γ·rt+1 + γ²·rt+2 + …      computed BACKWARDS, like Monte Carlo

rewards 1, 1, 1 with γ = 0.9:
  G3 = 1
  G2 = 1 + 0.9 × 1    = 1.9
  G1 = 1 + 0.9 × 1.9  = 2.71

Yes, this is Monte Carlo (booklet 02): REINFORCE waits for the game to end, then walks backwards.

The baseline: compare with "normal"

In CartPole every reward is +1, so every G is positive, and without a baseline every action gets pushed up, the good ones just a bit more. That works on average but is very noisy. Subtract a baseline b, "what's a normal result?":

θ  ←  θ  +  α · (Gt − b) · ∇ log π(at | st)

Real output of bandit_pg.py part 1 (same pull: arm 1, r = 3.0):

Baseline bG − bNew πWhat happened to arm 1
0 (none)+3.0[0.299, 0.403, 0.299]pushed up a lot
2.5+0.5[0.328, 0.345, 0.328]pushed up a little: "a bit better than normal"
3.5−0.5[0.339, 0.322, 0.339]pushed down: "3.0 is worse than normal"

Why the baseline doesn't change the answer, only the noise

Average of b · ∇log π(a)  =  b · Σa π(a)·∇log π(a)  =  b · Σa ∇π(a)  =  b · ∇(Σa π(a))  =  b · ∇(1)  =  0

The probabilities always add up to 1, and the derivative of a constant is 0. So subtracting b adds zero on average: same direction, much less jumping around.

Worked example 3: below-average results get pushed down

CartPole-like: h = [0, 0] → π = [0.5, 0.5].  Pushed RIGHT, the return-to-go was G = 10.  α = 0.01
∇log π(right) = [−0.5, +0.5]

no baseline:   h += 0.01 × 10 × [−0.5, 0.5] = [−0.05, +0.05]   π(right) = e0.05/(e0.05+e−0.05) = 0.525
baseline b=12: h += 0.01 × (10 − 12) × [−0.5, 0.5] = [+0.01, −0.01]   π(right) = 0.495

07The algorithm

Pseudocode

policy network πθ  (state → probabilities)
for each game:
    play until the end, sampling at ~ πθ(·|st);  store log π(at|st) and rt
    G = 0;  for t = T … 1:  G = rt + γ·G;  Gt = G           # returns-to-go, backwards
    b = average of the Gt                                       # simple baseline
    loss = − Σt (Gt − b) · log π(at|st)                       # minus: descent = ascent on J
    θ ← θ − lr · ∇loss                                                # backprop does ∇log π for us

08The code, line by line

reinforce.py

① The policy network: state in, probabilities out

class Policy(nn.Module):
    def __init__(self, n_inputs=4, n_actions=2, hidden=32):
        super().__init__()
        self.net = nn.Sequential(nn.Linear(n_inputs, hidden), nn.Tanh(), nn.Linear(hidden, n_actions))
    def forward(self, state):
        logits = self.net(state)                      # raw scores, any size
        return torch.softmax(logits, dim=-1)          # probabilities: positive, add up to 1

② Playing: roll the agent's own dice

probs = policy(torch.as_tensor(s, dtype=torch.float32))
dist = torch.distributions.Categorical(probs)
a = dist.sample()                             # ROLL THE AGENT'S DICE
log_probs.append(dist.log_prob(a))            # remember log π(a|s): needed for the gradient

③ Returns-to-go, backwards

running = 0.0
for t in reversed(range(len(rewards))):
    running = rewards[t] + gamma * running
    G[t] = running

④ The update

G = returns_to_go(rewards, gamma)
if baseline == "mean":
    G = G - G.mean()                                     # better or worse than normal?
loss = -(torch.as_tensor(G) * torch.stack(log_probs)).sum()
optimizer.zero_grad()
loss.backward()                                          # computes ∇log π for every weight
optimizer.step()                                         # θ ← θ + α·Σ (G_t − b)·∇log π
LineMeaning
torch.softmaxChapter 04: logits → probabilities.
dist.sample()The agent picks by chance. No ε needed: the probabilities themselves explore.
dist.log_prob(a)log π(a|s) of the action actually taken. PyTorch remembers how it depends on θ.
G - G.mean()The baseline: this game's average return-to-go. Above average → push up, below → push down.
the minus sign in lossOptimisers minimise. Minimising −J is the same as maximising J (gradient ascent).
loss.backward()Applies the chain rule through softmax and the network to get ∇log π for all weights at once.

What to notice

  • The baseline is the difference between working and not working. In CartPole every reward is +1, so without it every action is pushed up and the signal drowns in noise.
  • Returns-to-go matter even more. Crediting each action with the whole game's total (including rewards from before it) gave 32.5, barely above random (≈ 22).
  • Even the good version drops and recovers (games 220–320): one unlucky big update can make the policy worse. That's the problem PPO was invented to solve (booklet 06).

An honest lesson about generalisation

The policy is certain about the state it really meets (a pole spinning to the right → push right, 100%). But "leaning right while perfectly still" almost never happens in its own games: its pole is always moving a little. In those unfamiliar states its answers are unreliable, even though it scores a perfect 500 in real play. A network only learns well where it has experience, the same lesson as unvisited squares in FrozenLake. It also shows the policy mainly reacts to spin, not lean, which is a perfectly good strategy.

11Real-world problems

When policy gradients fit

✔ Randomness is part of the answer (games against opponents, exploration that must stay). ✔ Continuous or huge action spaces. ✔ You want to fine-tune an existing probabilistic model (a language model). ✘ Plain REINFORCE is too noisy and sample-hungry for most real problems: in practice people use its descendants, A2C (booklet 05) and PPO (booklet 06).

1 · Fine-tuning a language model

Statethe prompt plus the words written so far
Actionthe next word (token), chosen from the model's own probabilities
Rewardat the end of the reply: a score for how good the whole answer was (from a reward model trained on human preferences, see booklet 09)
Why policy gradientA language model already is a softmax policy over words. Increasing log π of words in highly rated answers is exactly this booklet's update. InstructGPT-style training used PPO, a refined policy gradient.

2 · A robot arm reaching for an object

Statejoint angles and speeds, object position (camera)
Actiontorque for each joint: continuous numbers. The policy outputs a mean and spread (a Gaussian) instead of softmax.
Reward−distance to the object each step, +10 when grasped
WhyNo max over infinitely many torques is needed: just roll the Gaussian dice and push up good actions. Pitfall: thousands of trials, so train in a simulator first.

3 · A pricing assistant that must keep testing

Stateday of week, stock level, competitor price band
Actionone of 5 discount levels, chosen with probabilities
Rewardprofit of the day
WhyA stochastic policy naturally keeps trying other prices a little, and never collapses to one price you can't learn from. A baseline (normal daily profit) is essential, because profit is very noisy. This is a "could be used for" scenario.

4 · Game strategy against people

Rock-paper-scissors in this booklet, and in real games like poker: when an opponent can adapt, a predictable policy loses. Policy-gradient methods (combined with self-play) are a standard tool in research on such games, where learned strategies must mix their moves.

13Clearing up the confusions

Does the policy network output an action, a value or probabilities?

Probabilities, one per action, adding up to 1. The action comes from rolling dice with them. There is no Q-value anywhere in plain REINFORCE.

Are these the same probabilities as FrozenLake's slipping?

No. π(a|s) is the agent's own choice probability, which it learns. Slipping is the world's behaviour, which it never learns directly and doesn't need to know.

Is there a Bellman equation in REINFORCE?

No. It uses the real returns G (Monte Carlo), not "one step + a guess". The Bellman idea comes back in actor-critic (booklet 05) through the critic.

Why log π and not π?

Because of the log-derivative trick: ∇π = π·∇log π turns the gradient into an average we can estimate by playing. Also, log turns the product of many small probabilities into a sum, which is numerically safer.

If every CartPole reward is positive, won't every action be pushed up?

Without a baseline, yes, and that's why it's noisy. It still works on average because better actions get pushed up more. The baseline fixes it: only better-than-normal actions go up.

Why is there a minus sign in the loss?

PyTorch's optimisers go downhill. We want to go uphill on reward, so we minimise −J.

Does it need ε for exploration?

No. Softmax never gives exactly 0, so every action keeps some chance. But the probabilities can become very close to 0, so exploration can still die out (some methods add an "entropy bonus" to prevent that; see A2C/PPO).

Why can't it reuse old games like DQN's replay buffer?

The gradient formula is an average over actions drawn from the current π. Old games were drawn from an older π, so they'd give the wrong average. (PPO fixes this partly with a probability ratio, booklet 06.)

Which state's probabilities get updated?

Every (state, action) of the finished game, each weighted by its own Gt − b. Because it's a network, nearby states change too.

Why did the agent never settle against the spy?

Because the spy keeps adapting: whatever you favour, it counters. Two learners chasing each other often cycle. The ideal answer (1/3 each) is a balance point that plain REINFORCE keeps overshooting.

REINFORCE in 9 lines 
π_θ = network → softmax
for each game:
  play to the end, a ~ π_θ(·|s)
  store log π(a|s), r
  G_t = r_t + γ G_t+1  (backwards)
  b = mean(G_t)
  loss = −Σ (G_t − b)·log π(a_t|s_t)
  backprop; optimizer step
  forget the game
Key formulas 
softmax: π_a = e^h_a / Σ e^h
∂log π_a/∂h_b = 1[a=b] − π_b
trick:   ∇π = π ∇log π
∇J = avg[ G · ∇log π(a|s) ]
update:  θ += α (G_t − b) ∇log π
baseline adds 0 on average
Four sentences to remember
  1. Policy-based methods learn the action probabilities π(a|s) directly and play by rolling their own dice.
  2. The log-derivative trick turns "the gradient of expected reward" into an average we can estimate by playing: G·∇log π.
  3. REINFORCE pushes up actions followed by better-than-normal returns and pushes down the rest; the baseline defines "normal".
  4. It's a Monte Carlo method: unbiased but noisy, and on-policy (old games can't be reused).
